# Contributing

This repository holds two Android apps in one Gradle build, and a module of
shared code they both compile.

**Field Kiosk** (`org.awana.kiosk`) is the Device Owner app installed on every
field device: a locked-down launcher for phones handed to non-technical,
sometimes non-literate users. **Field Kiosk Setup** (`org.awana.provision`) is
the trainer's app that provisions those devices over a local hotspot. It runs on
a normal, unmanaged phone — nothing in it is a Device Owner.

[README.md](README.md) describes what the apps do and how a deployment runs.
Read that first if you have not deployed with them. This file is the rest: how
to build and test, how the pieces fit, and which of the surprising bits are
deliberate.

## Repository layout

```
shared/           The wire protocol both apps compile: KioskConfig, PackageSpec,
                  WifiNetwork, EnrolmentReport, AdminPin, Certificates, DeviceLabel.
kiosk/policy/     DevicePolicyManager wrapper, config fetch, installer, provisioning.
                  No UI dependencies.
kiosk/launcher/   The HOME activity, icon grid, PIN entry, admin screen.
kiosk/app/        Assembly: the DeviceAdminReceiver, the boot receiver, the
                  provisioning service.
provision/        The trainer's app: APK library, deployment profiles, hotspot,
                  HTTP server, QR, dashboard.
sample/           Not shipped. A real APK for the end-to-end test to install.
tools/            test.sh and dev-keys.sh.
testdata/         The golden provisioning QR fixture.
docs/             Hardware checklist and the original specification.
```

Both apps are minSdk 30, targetSdk 36, built with JDK 17.

## Building

```sh
./gradlew :kiosk:app:assembleDebug     # the device app
./gradlew :provision:assembleDebug     # the trainer's app
./gradlew :kiosk:policy:assembleDebug  # one module alone
tools/dev-keys.sh                      # dev keystore and v3 lineage, both gitignored
```

`:provision` bundles the kiosk APK of the same build type into its own assets
through a Gradle task that depends on `:kiosk:app:assemble<Variant>`, so there
is no script to run and no APK committed anywhere. A debug trainer app carries a
debug kiosk and therefore provisions a debug fleet, which can never receive
production updates.

## Testing

```sh
tools/test.sh                           # the whole instrumented suite, both emulators
./gradlew :provision:testDebugUnitTest  # JVM: the QR payload and the golden fixture
```

`testdata/provisioning-qr.golden.json` is generated by the `:provision` unit
tests and parsed by a `:kiosk:app` instrumented test exactly as the receiver
would parse it, so a change to the QR shape on one side fails on the other.
Regenerate it after an intended change:

```sh
./gradlew :provision:testDebugUnitTest -Dgolden=write
```

### Two emulators, and why

| AVD | Role |
|---|---|
| `kiosk_aosp_30` | Device Owner. Policy, lock task, install verification, PIN logic. |
| `kiosk_ui_30` | Clean. Compose UI tests, and the trainer's app. |

On a device where the kiosk is Device Owner, the HOME activity and holding lock
task, **Compose's test harness sees no compose hierarchy at all** — every UI
test fails with "No compose hierarchies found", including a one-line smoke test.
`ComposeSmokeTest` is a canary for exactly that, because the symptom otherwise
reads like a bug in the screen under test. Hence the split.

Both AVDs must use an **AOSP** system image, not a Google Play one:
`dpm set-device-owner` fails if any account exists on the device, and Play
images acquire accounts readily. The image ABI has to match the host —
`arm64-v8a` on Apple Silicon, `x86_64` elsewhere.

```sh
sdkmanager "system-images;android-30;default;arm64-v8a"
avdmanager create avd -n kiosk_aosp_30 -k "system-images;android-30;default;arm64-v8a" -d pixel_5
avdmanager create avd -n kiosk_ui_30   -k "system-images;android-30;default;arm64-v8a" -d pixel_5

emulator -avd kiosk_aosp_30 -no-snapshot -no-boot-anim -no-audio &
```

A freshly created AVD needs its screen kept awake once, or the lock task tests
ANR when the screen sleeps mid-run:

```sh
adb shell svc power stayon true
```

Make the first one Device Owner once, after it boots:

```sh
adb -s "$(tools/test.sh --serial kiosk_aosp_30)" shell dpm set-device-owner \
  org.awana.kiosk/.KioskDeviceAdminReceiver
```

Once an AVD has a device owner, the only way to point it at a different package
is to wipe the AVD (`emulator -avd kiosk_aosp_30 -wipe-data`). Removing the
active admin returns the device to unmanaged but does not free the slot for
another package, so renaming the kiosk's application id means recreating the
AVD.

### Running one class or one test

Emulator serials are assigned by boot order, so resolve them by AVD name rather
than assuming a port. `tools/test.sh --serial <avd>` prints one.

```sh
SERIAL=$(tools/test.sh --serial kiosk_aosp_30)
ANDROID_SERIAL=$SERIAL ./gradlew :kiosk:app:connectedDebugAndroidTest \
  -Pandroid.testInstrumentationRunnerArguments.class=org.awana.kiosk.PolicyTest
ANDROID_SERIAL=$SERIAL ./gradlew :kiosk:app:connectedDebugAndroidTest \
  -Pandroid.testInstrumentationRunnerArguments.class=org.awana.kiosk.PolicyTest#provisionIsIdempotent
```

### Reading instrumented failures

Gradle prints only a pass/fail count for a connected run. The messages are in
the XML, under `kiosk/app/build/` for the kiosk and `provision/build/` for the
trainer's app:

```sh
python3 -c "
import glob, xml.etree.ElementTree as ET
for f in glob.glob('**/build/outputs/androidTest-results/connected/debug/*.xml', recursive=True):
    r = ET.parse(f).getroot()
    for tc in r.iter('testcase'):
        for fa in list(tc): print(tc.get('name'), (fa.text or '')[:600])
"
```

## Architecture

The seam that makes everything testable: **`onProfileProvisioningComplete` is a
thin wrapper over `Provisioner.provision(config)` and nothing else.** Tests call
`provision()` directly with a synthesised config, so the whole post-scan path —
fetch, verify, install, pre-grant, apply policy, join networks, report — runs
without a camera or a setup wizard. Do not grow logic into the receiver.

What the receiver does is read a bootstrap out of the provisioning extras and
hand it to a foreground service, because a receiver's process can be killed the
moment `onReceive` returns and the payload includes a download that can run to
hundreds of megabytes. Two further activities exist only for the platform's
provisioning handshake: `ACTION_GET_PROVISIONING_MODE`, which tells the setup
wizard this app is asking to be a Device Owner, and
`ACTION_ADMIN_POLICY_COMPLIANCE`, which the wizard shows while the policy is
being applied.

`DevicePolicy` resolves its own admin `ComponentName` by querying
`PackageManager` for the receiver in this package, so `:kiosk:policy` needs no
compile-time dependency on `:kiosk:app`, which declares it.

Every policy step is idempotent and independently re-runnable: a partial
provisioning failure in the field has to be recoverable from the admin screen
rather than by factory reset. Steps that fail are collected rather than thrown,
and end up in `EnrolmentReport.failures`, where the trainer's dashboard shows
them.

On the trainer's side, `ProvisioningSession` is the centre of the app. A
foreground service holds a hotspot and a NanoHTTPD server for as long as devices
are enrolling, because releasing the hotspot reservation kills the hotspot. The
server has five endpoints: `/dpc.apk` for the setup wizard, `/config.json` and
`/apks/{package}.apk` for the kiosk, `/manifest.json` for diagnosis, and
`POST /report` for enrolment reports.

There is no DI framework and no `Application` subclass: classes construct their
few collaborators directly. The maintaining team works in React Native, not
Kotlin. Prefer boring code; every dependency is a maintenance liability.

## Things that look like bugs but are deliberate

**`DISALLOW_FACTORY_RESET`, `DISALLOW_DEBUGGING_FEATURES` and
`DISALLOW_INSTALL_UNKNOWN_SOURCES` are not set.** They are listed in
`DevicePolicy.NOT_SET_BY_DESIGN` and a test asserts they stay unset. A device
that cannot be recovered in the field is worse than any escape it prevents, and
blocking unknown sources would break third-party self-updaters. Leaving the
debugging restriction unset is not the same as having a recovery route, though:
a QR-provisioned phone has USB debugging off and Developer options out of reach.

**Network restrictions are applied last**, after install and reporting, not in
one block up front — locking down Wi-Fi configuration must not disturb the
hotspot the payload arrives over.

**The kiosk joins the deployment's Wi-Fi networks itself, at provisioning.**
With `DISALLOW_CONFIG_WIFI` set a user cannot add one, so without this a team's
sync network would be unreachable on every phone unless a trainer typed it in
behind the admin PIN.

**The admin screen can add a Wi-Fi network, not just toggle the radio.** Same
reason, for networks nobody knew about at provisioning time. A Device Owner is
exempt from `addNetwork`'s deprecation.

**Nothing runs at process start.** The launcher is the HOME activity, and
anything that delays its first window past the five seconds `InputDispatcher`
waits before declaring "does not have a focused window" gets the activity
ANR-killed at boot. WorkManager's automatic initialiser did exactly that once.
Any new startup work has to be measured the same way, on the slowest phone in
the fleet.

**The QR carries a bootstrap, not the config.** `onProfileProvisioningComplete`
reads only a server URL and a SHA-256; `ConfigFetch` then downloads
`/config.json` and refuses it unless the bytes hash to that value. The config
used to be embedded, where it grew about 200 bytes per app — 2218 bytes
pretty-printed for two apps, 1579 compact — and stopped encoding at all around
eight of them. The bootstrap is a constant 980 bytes however large the
deployment is.

The hash is load-bearing, not decorative. The QR is the only part of the flow
with end-to-end integrity: anyone who scanned it can join the hotspot and
impersonate the gateway, and a substituted `adminPinHash` would hand over the
device. Both sides hash the bytes **as served**. Re-encode on either side and
every device rejects a genuine config.

**First-install verification trusts the fingerprint in the config**, and the
QR's hash is what protects it. There is no incumbent package for Android to
compare against on a first install, so this is the only point at which a
substituted APK can be caught at all.

**`Certificates.matches` checks the whole certificate history**, not just the
current signer, so a package that has rotated its key under APK Signature Scheme
v3 still verifies against a fingerprint recorded beforehand.

**The kiosk APK's signature checksum is computed at runtime** from the APK being
served, not hardcoded, so debug and release builds both work and there is no
constant to forget at release time.

**Plain HTTP is correct on the provisioning hotspot.** Integrity comes from the
signature checksum in the QR and from the certificate checks the kiosk performs
itself, not from the transport. The hotspot has no certificate to present.

**The gateway address is read, never hardcoded.** It is commonly `192.168.43.1`
but varies by OEM.

**`Hotspot` is an interface with a fake.** `startLocalOnlyHotspot` does not
exist on an emulator, and its behaviour on budget phones is inconsistent enough
that a manual fallback is needed in the field anyway.

**`:sample` exists only to give the end-to-end test a real APK to install.** It
is not shipped. The test cannot install the kiosk over itself mid-run, and a
hand-made file would exercise neither the certificate reader nor
`PackageInstaller`.

## Decisions

The reasoning behind the choices that go beyond the original specification.

**One build, one shared module.** The two apps were separate repositories with
the config and report types duplicated between them, guarded against drift by a
golden fixture checked into both. They are now one Gradle build compiling one
`shared/` module, so the wire format cannot drift at all. The fixture is kept
because it still catches changes to the QR shape itself, which is the part
neither type system covers.

**Nothing in either app is specific to one field app.** There is no pinned
certificate, no hardcoded permission list and no built-in update channel. Each
`PackageSpec` carries the certificate fingerprint and the runtime permissions
the trainer's app read out of the APK when it was added to the library, and the
kiosk grants only the permissions the installed build actually requests — a
`maxSdkVersion` on the trainer's phone may have kept a permission this device's
Android version drops. Foreground location has to precede background location or
the background grant is refused, which is why the order in the list is
preserved.

**The trainer populates the APK library.** Awana does not redistribute
third-party APKs, which keeps a trademark and policy question out of the
deployment process entirely. Everything except the kiosk itself is added from
device storage, and the fingerprint is shown in the UI, published in
`/manifest.json` and carried in the config, so a device can refuse an app that
does not match it. That check is what stops a trainer being talked into
deploying a fake app across a whole team at once.

**The enrolment report is a product feature, not telemetry.** It is what turns a
fiddly technical sequence into something a trainer can watch and act on. Each
device gets a four-character label derived from its id, in an alphabet with no
0/O or 1/I, so six identical handsets can be told apart and the code read aloud.

**`deploymentId` is the trainer app's profile id**, so devices enrolled in
different sessions of the same deployment still belong together.

**The hotspot's security type is checked against what the QR can express.**
`EXTRA_PROVISIONING_WIFI_SECURITY_TYPE` accepts only `NONE`, `WPA`, `WEP` and
`EAP`; a local-only hotspot can hand back WPA3-SAE, which cannot be expressed at
all. The app routes that case to the manual tethering fallback rather than
emitting a QR that silently fails to connect.

**Keep the QR payload under `QrPayload.COMFORTABLE_BYTES`.** Beyond that the
code needs enough modules that a budget phone camera struggles in poor light. A
test asserts the size of the golden payload.

**The launcher was written from scratch** rather than forked from a
general-purpose launcher: an app drawer, widgets, folders, gestures, icon packs
and a wallpaper picker are each either dead weight or an escape route. It loads
its app list off the main thread and rasterises icons once, rather than doing
disk and `PackageManager` work during composition.

**The PIN rate limiter uses elapsed realtime, not the wall clock.** The kiosk
sets `setAutoTimeEnabled`, so the wall clock can jump backwards on first sync
and would otherwise hand an attacker a free reset.

**Dependencies, and why each is there:** NanoHTTPD for the provisioning server,
ZXing `core` alone for QR encoding, kotlinx-serialization for the wire format,
and the platform's `PBKDF2WithHmacSHA256` for the admin PIN. There is nothing
else on purpose.

**There is no updater yet.** The admin screen can install an app from a URL, and
running a session again re-provisions a device, but nothing polls for new
versions. When one is written, the update source belongs behind a small
interface so an offline channel is a cheap addition rather than a rewrite.

The original implementation handoff is kept for the record at
[docs/handoff-spec.md](docs/handoff-spec.md). It predates the rename and the
fetched-config design, so where it and this file disagree, this file is right.

## Facts established about CoMapeo

CoMapeo was the first deployment target. Nothing in the code refers to it any
more, but these were expensive to establish and should not have to be
re-derived by whoever deploys it next.

- Its package is **`com.comapeo`**. The specification's §5.5 example says
  `app.comapeo` and is wrong.
- Its release certificate SHA-256 is
  `f88123ed1f334792c07f1df20ac91038ed2569c3f93f46acb482462d1daf7054`.
- It ships as a **single universal APK** of about 186 MB, arm64-v8a plus
  armeabi-v7a, signed with v2 and v3 and no v1 JAR signature. It is not a split
  install, so the specification's split-install concern does not apply.
- It declares `SYSTEM_ALERT_WINDOW`, which is an app-op rather than a runtime
  permission and **cannot** be pre-granted by a Device Owner.
- `DevicePolicyManager.setApplicationExemptions` is not in the public SDK, so
  there is no doze exemption at any API level. `setUserControlDisabledPackages`
  is the ceiling.

## Signing

One key signs both apps, from one `keystore.properties` at the repository root.
**If that key is lost, no enrolled device can ever receive a kiosk update and
the only remedy is factory resetting every fleet.** Read [KEYS.md](KEYS.md)
before touching any signing config. Without `keystore.properties` the release
build silently falls back to debug signing — check `buildVariant` in the admin
screen or in an enrolment report rather than assuming.

## Conventions

Strings are all externalised and written for a non-technical reader in the
deployment locale. Error text says what to do, not what failed. Destructive
actions state their consequence in plain language before they happen.

The people operating the trainer's app are partner trainers, not engineers and
not Awana staff. Caveats belong inline in the UI at the moment a choice is made
— `showNotificationShadeCaveats` sits next to the toggle it describes — rather
than in documentation a trainer has to go and find.

Comment the *why*, not the *what*, and only where the why is not obvious: a
hidden constraint, a subtle invariant, a workaround for a specific bug. Anything
needing three lines of prose belongs in the commit message or the pull request
instead.
